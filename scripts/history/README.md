# 整理 fork 提交历史

发正式版前、追上游前各整理一次: 把测稳了的提交合并, 减少「同一个上游文件被好几条提交反复改」——
追上游时每条改到上游文件的提交都要对那个文件解一遍冲突。

## 哪些能动

- 只动**测满一周**的提交: 它的改动进过一个发布满 7 天的 release。按内容判断 (`tested.py`), 不看提交在栈里的位置与提交时间。
  没测满的原样留着, 不合并, 也不往里并东西。
- 修复只有两种单独留: 风险不确定、出问题要能单独撤的; 修上游代码、上游可能也会修的 (追上游时上游修了就整条丢)。
  其余修复并回它修的那条提交。并之前把修复里不显然的约束写成代码注释, 提交说明并掉之后就看不到了。
- 功能: 可能整个撤掉的单独一条; 其余的同一功能合成一条, 或并回基线。
- 删上游代码的提交 (上游 TV 客户端、Ani 账号功能) 保持独立, 追上游时靠它们「保持删除」。
- 发版说明模板只在链尾那条 `docs` 里改。

## 步骤

1. `tested.py <上游基点>`: 每条提交的新增行在各个 release tag 里的比例, 找出测满一周的范围。
2. `cells.py <上游基点> --overlap <基线序号,…>`: 每条提交改了几个上游文件、与基线共改几个; 合并能省多少格子。
   只改 fork 自己文件的提交, 并不并对追上游没影响, 冲突就不并。
3. `movable.py <上游基点> --to <基线序号> <候选序号…> --json mov.json`: 一组候选一起往前并进基线时, 逐个文件判断挪不挪得动、
   卡在哪一条。整条能挪的整条并; 只有几个文件挪不动的, 计划里用 `SPLITS` 把能挪的文件分给基线, 其余留下 (可以读 mov.json 生成)。
4. 照 `plan-template.py` 在临时目录写计划, `regroup.py dry <plan.py> [--stop]` 空跑, 按报出的冲突改计划直到 OK。
   dry 只写对象, 不碰工作区、索引与分支; 结果 (`mapping.txt`、`new_tip.txt`) 写在计划旁边。之后 `cells.py --compare <新链尾>` 量省了多少。
5. 分组方案给用户看。终树与原链尾相同时不用另编; 不同 (有意改了内容) 时在临时 worktree 检出新链尾, TV 与手机两个变体都编一遍。
6. 动手前查设备登记表与在线会话, 别在别的会话提交到一半时改写。`regroup.py land <plan.py>`: 打备份 tag,
   CAS 挪 main (dry 之后 main 又多了提交时用 `git replay` 接上)。终树不变, 检出 main 的工作区不用动。
7. 通知在线会话 (SHA 全换)。基于旧 main 的分支用 `git rebase --onto <新 main> <旧 main> <分支>` 接上, 不会冲突。

## 冲突的常见原因

- 往前挪的提交依赖中间某条留着的提交 (例: 输入框修复改到了多用户加的页面): 用 `SPLITS` 把那几个文件分给它依赖的那条。
  别用 `"latest"` 把 fork 的修复分进上游修复那几条 (它们要保持能整条丢掉)。
- `strings_izuko.xml`、控制台页面这类每个功能都往里加一段的文件: 挪过别的功能就冲突。按 key 合并也不行 (条目插在文件中间,
  合并会改顺序, 终树对不上)。这类提交只改 fork 自己的文件, 不并对追上游没影响, 留着单独一条。
- 往后挪一条提交, 它后面改同一文件的提交全失去上下文, 一次报十几处冲突全是连锁; 往后挪冲突不能分段, 只能放弃。

## agents 文件

fork 里改 AGENTS.md / CLAUDE.md / `.agents/**` / `.claude/**` 的内容只放在一条 `chore(agents): 智能体规则与测试技能` 里,
功能提交不夹带。改了要提交时跑 `fold-agents.py <自己改的路径>… [--message <说明文件>]`, 看过报出的新链尾再加 `--apply`:
并进那一条, 之后的提交只换树里这几个路径、原样重放, 不碰工作区, 打备份 tag 后 CAS 挪 main。挪完照上面第 7 步通知在线会话。
