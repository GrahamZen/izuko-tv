# 一起看

几个人各自在自己的设备上播同一集, 成员的播放、暂停、位置、倍速、换集跟着房主。应用没有自己的服务器,
房间里的消息经公共 MQTT 代理转发; 消息只在状态变化的时刻发, 其余时间各端按最后一条状态自己推算。

代码在 `app/shared/app-data/src/commonMain/kotlin/domain/together/`。

## 通道

通道只管把一段字节送给房间里的其他人, 不关心内容。

| 文件 | 职责 |
|---|---|
| `TogetherChannel.kt` | 接口 `TogetherChannel` 与实现 `MqttTogetherChannel`: 同时连几家代理, 每条消息每家都发, 收到重复的丢掉 |
| `TogetherCrypto.kt` | `TogetherRoomKey` (房间号 → 话题名, 房间号 + 密码 → 密钥) 与 `TogetherEnvelope` (一条消息在线上的样子, 以及「解不开」的回执) |
| `TogetherBrokers.kt` | 代理清单 `TogetherBrokerList` (仓库根目录的 `together-brokers.json`, 包里不带代理地址) 与没有清单时的 `TogetherNoBrokersException`; 给 HTTP 客户端装 WebSocket 插件的特性 `TogetherWebSocketsFeature` |
| `mqtt/MqttPackets.kt` | MQTT 3.1.1 里用到的那几种报文的编解码 |
| `mqtt/MqttTransport.kt` | 一条字节管道 `MqttTransport`; 实现是 MQTT over WebSocket, 走应用的 HTTP 客户端 |
| `mqtt/MqttLink.kt` | 与一家代理之间的一条连接: 握手、订阅、心跳、断线重连、遗嘱 |

### 为什么是公共 MQTT 代理

- 同步消息很小也很少 (状态变化时一条, 几百字节), 用不着点对点连接; 跨 NAT 的点对点本身也离不开牵线的服务器。
- 公共代理不用注册, 发布 / 订阅正好是「一个人发、房间里其他人收」。
- 走 WebSocket 而不是裸 TCP: 这样经过应用的 HTTP 客户端, 跟着应用的代理设置走, 各平台也都有。

### 约束

- **房间里的人必须落在同一家代理才互相看得到。** 所以是每家都连、每家都发、按消息标识去重,
  不是「连不上再换下一家」(两边会换到不同的家)。只要双方有一家都连得上, 房间就通。
- **连哪几家全看仓库里的清单** (`together-brokers.json`, 通用的 `RepoHostedList`: 每天拉一次, 拉不到用上次存下的), 包里不带代理地址:
  代理被封、下线, 或要补大陆连得上的代理时改清单, 不用发版 (清单从 GitHub 的 main 分支拉, 推上去才生效)。清单只认 `wss://` 地址。
  每次开通道时取当时的清单, 已连着的不跟着换。一次都没拉到过 (刚装好、应用启动时那次没拉到) 时, 开房间或加入前当场再拉一次,
  还是没有就失败, 电视与控制台提示「暂时无法获取一起看的服务器列表」(`TogetherNoBrokersException`); 回到记住的房间时照常隔一会儿重试。
  1.0.9-alpha04 及以前的包只认包里带的三家 (emqx / hivemq / mosquitto), 清单里要一直留着其中至少一家, 不然新旧版本的人进不了同一个房间
  (`TogetherBrokersFileTest` 守着仓库里的清单)。
- **几家代理不是同时连上的, 各人连得上的也不一样。** 各家各连各的, 互不等待。代理的域名解析出好几个地址, IPv6 的排在前面,
  而有的网络上它们的 IPv6 地址连不通 (能 ping 通, TCP 连不上): 连不通的地址要等满连接超时才换下一个, 所以连接超时只给 3 秒
  (客户端默认 30 秒, 那样一家代理要一两分钟才连上)。即便这样, 某一家晚几秒到十几秒才连上仍是常态,
  「连上了」不是一个时刻: 每多连上一家, 上层都要往那一家再说一遍 (见「房间」)。
- **公共代理谁都能订阅、谁都能发。** 话题名由房间号、密钥由房间号加密码经慢哈希 (PBKDF2) 算出: 话题名里看不出房间号,
  也不带应用的名字; 消息做带校验的加密 (AES-256-GCM), 不知道密码的人读不了也伪造不了。
  连接用的客户端标识是随机串。慢哈希 2 万轮, 慢的电视上一次约一秒; 轮数定下后不能改 (各台设备要算出同一个话题与密钥)。
  最近一个房间号的话题名、最近一组房间号加密码的密钥留在内存里 (`TogetherRoomKeyCache`):
  断网时自动回房每隔一会儿重试、房主让位后重新进, 都不重算。
- **密码不对的人与房间在同一个话题上**, 消息互相解不开。房主那一端 (`TogetherChannel.answersStrangers`) 对解不开的消息回一张不加密的回执
  (`TogetherEnvelope.deny`, 只带被拒那条消息的标识), 同一条只回一次, 每分钟至多 20 张; 发的人对上自己最近发过的消息,
  就知道密码不对 (`TogetherChannel.rejections`)。回执不加密: 知道房间号的人能伪造它, 让加入失败或把成员请出房间, 但读不了也改不了房间里的内容。
- **房间里只发用得上的。** 一个人往房间里发的是昵称、跟不跟随、在看哪一集看到哪; 头像地址这类界面不显示的不发。
- **消息不补发。** 用的是 QoS 0, 断线期间别人发的收不到。上层从 `TogetherChannel.links` 知道重新连上了,
  再跟房间对一次状态。
- **异常掉线靠遗嘱。** 每条连接向代理留一份遗嘱, 连接异常断开时代理把它发给房间; 主动离开时先发 DISCONNECT,
  代理不发遗嘱。几家代理各留各的, 所以只断了其中一家时房间里也会收到一份, 上层要把它当「可能掉线了」处理。
- **连接是否还活着**由 MQTT 的心跳 (PINGREQ / PINGRESP) 判断, 那是协议层的两个字节, 不是房间里的消息。
- iOS 上没有接加密 (`TogetherCrypto.ios.kt`), 进不了房间。

## 房间

房间有一个房主, 其他人是成员。房间的全貌 (谁在、各自在看什么、房主播到哪) 由**房主的设备**汇总 —— 这是没有服务器时顶替服务器的那一份:
成员把自己的状态发给房主, 房主记进名单、版本加一, 把整份快照发回房间。成员之间不对话。

| 文件 | 职责 |
|---|---|
| `TogetherRoomModels.kt` | 数据: `TogetherWatchingInfo` (在看什么、看到哪)、`TogetherRoomSnapshot` (房间快照)、房间里的消息 `TogetherMessage` 与编解码 (认不出的类型解成 null 丢掉, 旧版本收到新消息不出错) |
| `TogetherRoomHost.kt` | `TogetherRoomHost`: 房主那份名单, 只管名单与版本, 不碰网络与计时; `TogetherRoomClock`: 房间时间 |
| `TogetherRoom.kt` | `TogetherRoomGateway.join` (进房流程) 与一个房间的处理循环 (成员、房主各一个分支) |

### 谁是房主

- **开房间的那台设备。** 房间号就是设备号 (`TogetherSettings.deviceNumber`, 8 位, 第一次用时随机生成, 之后不变), 只有这台设备开这个房间
  (`TogetherRoomGateway.join(asHost = true)`): 当场就是房主, 不等谁回应。
- **加入 = 找房主。** 加入时发一条招呼, 3 秒内有房主回应就当成员。等回应的途中看到房主的快照 (房主在, 只是招呼没送到) 就再打招呼,
  最多三轮, 之后按看到的快照当成员; 什么都没看到也再等一轮, 两轮 (6 秒) 都没有就是房间里没有房主, 加入失败
  (`TogetherRoomEmptyException`), 不会自己当房主。房主回执说解不开时当场失败 (`TogetherWrongPasswordException`)。
  等回应期间每多连上一家代理就再打一次招呼, 并从那一刻起至少再等 1.5 秒: 房主可能只在后连上的那一家上。
  房主回应这次进房的哪一次招呼都算数。
- **房主主动离开 = 解散**: 发一份 `CLOSED` 的快照, 带关闭的原因 (`TogetherCloseReason`: 解散 / 换了密码), 成员的房间到此结束。
- **房主换密码** = 以「换了密码」关掉房间, 用新密码重开。离线没收到关闭快照的成员, 回来打招呼时房主回执解不开, 他的房间以 `Rejected` 结束。
- **房主异常掉线 = 等他回来**: 成员不接任。房主用同一个编号回来后重新建房, 成员照样认 (同一个房主、版本更大), 发现名单里没有自己就再打招呼。
  所以成员编号要长期不变, 版本号从建房时刻的毫秒数起步。
- **出现两个房主时** (同一个房间号开在了两台设备上, 比如数据搬到新电视后旧电视也还开着): 两个房主互相看到对方的快照, 在线成员多的留下, 一样多时编号小的留下。
  让位的那个发 `Handover` 告诉自己的成员改听对方, 自己的房间以 `HostChanged` 结束, 重新进就是成员。
  成员平时只听当前房主的快照; 当前房主掉线之后才会改听别的房主。
- **转让房主** (房主在名单上选一个在线的成员, `TogetherManager.transferHost`): 临时的, 房间号与密码不变。
  1. 房主发 `TransferHost(to = 乙)`。那条消息不补发, 等的途中每个节拍 (2 秒) 再说一遍, 最多等 15 秒。
  2. 乙收到后自己的房间以 `PromotedToHost` 结束 (不说再见), 总管把记住的房间改成「自己当房主」(`own = true`), 以房主身份重开这个房间。
  3. 原来的房主看到乙的快照就让位: 乙那边名单里只有自己, 按人数比本该让回去, 但他是被请来的, 不比人数。之后同上一条: `Handover` 让别的成员改听乙,
     自己以 `HostChanged` 结束, 重新进当成员。
  4. 15 秒等不到 (乙是不认得这条消息的旧版本、掉线了、开不了房间) 就作罢 (`TransferFailed`), 还是原来的房主。乙后来才开成的话,
     两个房主按上一条收敛 (原来的人多, 乙让回去)。
  
  密码只有房间的主人 (房间号是自己设备号的那台, `TogetherSession.ownsRoom`) 能换: 被请来的房主看不到「更换密码」, 总管也不让换
  (换密码要关掉房间、用新密码重开, 而乙的设置里存的不是这个房间的密码)。解散照常可以。
  换房主的那一阵大家都在跟着去找新房主, 名单会乱 (先只有新房主, 别人陆续回来): 20 秒内原来名单上的人进出不提示, 只提示一次「X 已成为房主」
  (房主换了人, 包括原来的房主不在了换成别人), 新房主自己提示「你已成为房主」。
  让位的与被请去的都要关掉原来的连接、以新身份重新连代理再进房, 慢的设备上要好几秒 (索尼实测约 10 秒): 这一阵状态是
  `TogetherState.Joining(handoff = true)`, 电视弹窗与控制台卡片写「正在切换房主…」, 不显示成没在房间里; 播放照常, 回到房间后再对齐。

### 时间

各人的播放位置都带一个采样时刻, 用的是**房间时间** = 房主设备的时钟。成员靠一来一回量出自己的时钟与它的差:
发出时刻带过去, 房主原样带回并附上房间时间, 取来回的中点。量的机会: 进房 (以及断线回来) 时招呼的回应, 加上进房后再问的
一轮 4 次 (`TimeQuery` / `TimeReply`, 处理循环每 2 秒的节拍问一次), 之后每 5 分钟一轮。
取中点的误差最多是来回时间的一半, 而它会成为成员与房主之间的固定偏差 (超过 1 秒时每次接着播都要跳), 所以一轮里只认来回更快的那次;
新一轮的第一次直接替换旧的 (两边的时钟会慢慢走偏)。来回超过 2 秒的那次不准, 已经有差值时不用。
量好的差写进成员的日志 (`[一起看] 对表: 房主的系统时钟比本机快 / 慢 … ms, 消息往返 … ms`, 变了 0.2 秒以上才再写):
房间时间就是房主的系统时间, 两台设备的系统时钟可以差好几秒 (工单 54: 7 秒), 对照几台设备的日志要按这个差把时间对齐。

快照都带着发出时的房间时间。成员收到一份刚发出的快照, 它带的时间跟自己推算的差 3 秒以上, 就是有一边的时钟被系统对时拨动过
(或者进房时没量成): 之前量的都不作数, 重新打一次招呼再量一轮。

### 掉线

- 遗嘱 (`Bye(dropped = true)`) 到了不马上算数, 10 秒内没有那个人的任何消息才算: 几家代理各发各的遗嘱, 只断了其中一家时人其实还在。
  自己这边断了一家、还连着别家时主动发一条消息 (成员发一次状态, 房主发一次快照), 对面就知道人还在。
- **遗嘱可能来得很晚。** 断网几秒又连上的人, 他那条旧连接要等代理按心跳超时 (几十秒) 才被认定死了, 遗嘱那时才发,
  而房间里没有定时消息, 没人会碰巧在它之后说话。所以怀疑谁掉线了就问一次, 人在就会回应:
  房主收到成员的遗嘱时发 `Ping` (没回应就每两秒再问), 成员回一次状态; 成员收到房主的遗嘱时再打一次招呼。
  成员在快照里看到自己被标成了掉线 (那一问一答丢了) 也重新打招呼。
- **房主一直不应也算掉线。** 成员每次打招呼都开始等房主的消息, 10 秒内一条都没有就把房主标成掉线 (中途再问一次)。
  成员离线期间房主解散了房间或走了, 那条消息成员收不到, 靠这个才知道。两种时候不急着下结论: 还有代理没连上时
  (房主可能只在那一家上) 等到 45 秒; 自己不在线时不算, 连回来之后重新计时; 刚多连上一家时先等 1.5 秒那一家上的回应。
- 成员掉线: 房主在名单里把他标成 `DISCONNECTED`, 从标的那一刻起 5 分钟没回来就从名单里去掉。
- 没处理的: 成员正常离开的那条 `Bye` 只发一次, 房主那一刻恰好不在线就收不到, 这个人会一直留在名单里 (显示成「没在播放」)。
- 房主掉线: 成员各自把手上快照里的房主标成 `DISCONNECTED` (这份快照是本机改的, 版本不变)。
- 自己断线后又连上: 成员重新打招呼拿一份快照并重新对表, 房主把快照再发一遍。
- 本来就连着, 又多连上一家: 做法同上。房间里可能有人只在这一家上, 还没听到过这边;
  两个互相听不到的房主也是这样才看到对方、收敛成一个。

## 同步

行为照上游的一起看: 房主的播放状态就是房间的, 成员跟着房主。

| 文件 | 职责 |
|---|---|
| `TogetherManager.kt` | `TogetherManager`: 进出房间、把本机状态告诉房间、跟随房主时给播放页发指令; `TogetherSession` 是在一个房间里的这一段 |
| `TogetherSync.kt` | `SyncGuidanceEngine` (怎样才能跟房主在同一集)、`TogetherPlaybackBridge` (一起看与播放页之间的接头)、`PlaybackAutomationGate` |
| `data/models/preference/TogetherSettings.kt` | 跟不跟随房主、最近的房间、没离开的房间、这台设备的成员编号、设备号与自己房间的密码。换电视时不搬 (`DeviceMigrationMerge.DEVICE_PREFERENCE_KEYS`): 两台用同一个设备号会打开同一个房间, 成员编号也一样, 互相把对方的消息当成自己的丢掉 |

### 跟随的成员

- **被带到房主那一集**: 开始跟随时、房主换集时、房主进出播放页时、掉线的房主回来时算一次 —— 不在播放页就打开那一集 (`TogetherEffect.Navigate`),
  在别的番的播放页先退出再打开, 同一部番的另一集就地换集, 已经在同一集就对齐一次。播放页里自己换到别的集会被拉回去。
- **房主只在后台准备着时, 成员也只在后台准备。** 房主报的状态带着播放页在不在眼前 (`TogetherWatchingInfo.onScreen`; 动作面板「在后台准备」,
  或退出播放页后会话留在后台时为假, 停着进出播放页也单独报一次)。这时不在播放页的成员不进播放页, 由 `TvTogetherHost` 经
  `PlaybackSessionEntry.startInBackground` 在后台把同一集准备好 (`Navigate.inBackground`); 房主进了播放页再把人带进去,
  拿到的就是准备好的那个会话。正开着别的番的播放页的成员照常带进去; 不保留会话的形态什么都不做, 等房主进播放页。
- **只对着眼前的播放页做。** 电视退出播放页后播放会话还留在后台 (被按成暂停), 应用退到后台时播放页还开着、播放器同样被按停;
  这两种时候 `TogetherPlaybackBridge.localWatching` 仍有值, 但人没在看。两个判据都取自 `PlaybackActivity`:
  - `isPlayerInFront` (播放页是栈顶那一页, 应用也在前台) 为假时不纠正, 不照房主的状态去动播放器 —— 那会跟「不在眼前就按暂停」较劲。
    人回到播放页下一秒就对上。
  - `isPlayerOnScreen` (播放页是栈顶那一页) 为假时, 房主换集按「不在播放页」处理、把人带进那一集。
  - `isAppForeground` 为假 (按 HOME 去了别的应用) 时跟随的事一件都不做: 不在后台改页面, 也不让后台的会话去加载新的一集
    (加载完会响一下才被按停)。该带人去房主那一集而没带的记在 `TogetherSession.guidancePending`, 回到前台时由每秒的那一轮补上。
  应用在不在前台由根部的 `ReportAppForegroundToPlaybackActivity` 上报, 与要不要保留播放会话的设置无关;
  那个设置关掉时 `RetainedPlaybackSessionHolder.endRetention` 把「是栈顶那一页」复位成真。
- **房主掉线期间不跟随。** 手上的房主状态已经过时: 不纠正, 导航守卫与自动行为让路都撤掉, 成员可以自己去看别的。房主回来再接上。
- **每秒对一次**: 位置差 3 秒以上、播放 / 暂停不一样、倍速不一样, 就给播放页发 `PlaybackDirective.Sync`。只看本机手上的房主状态, 不发消息。
  所以成员自己按暂停、拖动会被拉回去。
- **自己的片源跟不上时落后着播** (`TogetherFollowerPace`): 成员自己在缓冲、加载, 或播放页正在一轮对齐里时不按位置纠正;
  自己落后的纠正两次隔不到 1 分钟就认定跟不上 —— 不再按位置往前跳 (每跳一次都扔掉已缓冲的, 慢的片源会一直播不起来),
  落后着连续播, 提示一次 (`TogetherEffect.FallingBehind`, 日志 `keeps falling behind the host`)。只算落在房主后面的纠正: 跑到房主前面
  (自己拖了进度、房主停着自己却在播) 的总是拉回去, 不算跟不上 —— 那与片源快慢无关, 算进去会弹「落后」、之后还不再纠正。房主自己跳了位置、暂停 / 继续照样跟; 连续顺畅播满 1 分钟或换了片源再试着跟上。
  播放页那一侧: 跳过去 4 秒还没播起来就算片源慢, 这一轮不再补跳, 这次的落点也不拿来学往前多跳多少。
- **房主卡住时等他**: 房主缓冲或加载时 (`TogetherWatchingInfo.holding`), 成员也该停着; 比的是「房主的画面在不在走」与「成员想不想播」。
  播放页等满 2 秒才真停下 (一闪而过的缓冲不管), 停在房主的位置上, 房主好了一起接着播。
- **不能自己进别的播放页**: 登记了导航守卫 (`EpisodeNavigationGuardRegistry`), 只放行房主那一集。
- **本机的自动行为让路**: `PlaybackAutomationGate.suppressed` 为真, 自动播下一集、从上次进度接着播这些不做。
- 关掉「跟随房主播放」是自由观看: 还在房间里, 上面几条都不生效。房主自己不受这些约束。

### 什么时候告诉房间

只在上一次说的状态推不出现在的状态时说: 进出播放页、换集、播放 / 暂停 / 缓冲 / 加载 / 倍速变了, 或位置与按上一次推算的差了 1.5 秒以上
(拖动, 或一点点偏出去)。没有定时上报。名字晚到或换了 (应用刚启动时账号信息还没读出来, `TogetherProfileProvider.changes`) 也再说一次:
房主空闲时不报状态, 不然一直显示成「观众 xxxx」。说的是播放会话的实际状态: 电视上人离开播放页、应用退到后台时会话被按成暂停,
房间里看到的就是暂停 —— 房主走开时跟随的成员停下等他。

### 播放页

`TogetherPlayerExtension` (播放器扩展, 登记在 `EpisodeViewModel` 的扩展清单里, 排在记忆进度前面) 是播放页这一侧:

- 把本机的播放状态写进 `TogetherPlaybackBridge`: 一进这一集先写一份「加载中」, 资源装进播放器之后每秒采样一次; 重新装资源的那一阵不写。
  位置是播放器在主线程上取样的 (每 0.1 秒), 主线程卡住时取样停在卡住前、读出来会落后好几秒 (索尼上见过一帧 2.6 秒), 照这个报出去别人会以为这边落后了:
  所以到主线程上去读, 等了超过 0.3 秒 (= 主线程刚卡过) 那一份就不写。播放器自己的线程不受主线程卡顿影响, 别人照上一份往后推就对。
- 执行 `PlaybackDirective`: 播放 / 暂停比的是播放意图 (`playWhenReady`), 倍速直接跟 (房主的倍速菜单、长按确定键加速都是改倍速), 换集走 `switchEpisode`。
  播放器只在正在播时才真的下发倍速, 没在播时设回 1 倍不生效、恢复播放也不补 (mediamp 把 1 倍当成「不用管」): 设倍速那一刻没在播的, 播起来再设一次,
  不然成员缓冲时房主松开长按, 成员会一直以 2.5 倍在跑 (报上去的却是 1 倍), 位置越跑越前、隔几秒被拉回一次。
  倍速一变当场写进自己的状态 (不等每秒的节拍): 只靠节拍顺带的话, 长按加速的开始与结束各晚 0~1 秒, 成员能差出一秒多。
  房主刚加速的 10 秒里成员只跟倍速、不按位置跳 (`TogetherManager` 的 `SPEED_UP_SETTLE_MILLIS`): 改倍速时播放器常要停一下
  (开着隧道播放的要重配解码器, 索尼上 4 秒多), 这时带着 2.5 倍的提前量去跳很容易过头; 房主回到原速的那一下顺带对齐 (差 1 秒就跳), 不留下加速时卡出来的一两秒。
  跟随中的成员自己从倍速菜单 / 控制台调倍速不生效也不记住 (`EpisodeViewModel.setPlaybackSpeed`): 不然播放器被改回房主的倍速, 「记住播放倍速」记下的却是自己调的那一档,
  换集或退出房间后就按它播。长按确定键加速只改播放器、松手还原, 本来就不记, 由上面的对齐改回去。
- 位置差多少才跳: 画面正连着播时差 3 秒以上才跳 (跳一次要重新缓冲)。房主按了暂停时成员只停下, 差 3 秒以上 (房主停着拖了进度) 才跳:
  停的那一下比房主晚一段网络延迟, 接着播时同样晚一段, 两段抵掉, 不用暂停时对一次、接着播时再对一次。
  房主卡在缓冲上、成员停着等他时差 0.5 秒就对齐 (跳的那点缓冲藏在等的时间里); 从停着接着播的那一下差 1 秒就对齐。
- 房主的状态一变 (播放 / 暂停、缓冲、倍速、自己跳了) 当场对齐 (`TogetherManager.observeHostChanges`), 不等每秒那一轮,
  这样停下与接着播晚的都只是网络延迟; 每秒那一轮照常兜底。为对齐跳了 3 秒以上才提示「已与房主重新同步」, 小的对齐不提示; 房主自己快进快退后 5 秒内成员跟着跳的那一下也不提示 (是房主让跳的)。
- 跳过去要重新缓冲, 等播起来房主已经又往前走了。所以房主在播时落点比房主靠前一点: 跳一次大约要多久 (`TogetherPlaybackBridge.seekLeadMillis`,
  按 1 倍速记) 乘上房主的倍速。每次跳完等播起来, 量还落后多少, 「(多跳的 + 还落后的) ÷ 倍速」就是这次跳花的时间, 与之前的估计取平均记给下一次
  (`nextSeekLead`, 上限 5 秒; 还没量过时直接用这次的)。不整个照搬: 同一台设备跳一次的耗时很飘 —— 工单 54 的 TCL 跳到没缓冲的地方 2.25 秒、
  缓冲范围里 1 秒, 照搬时落后 1.2 秒补跳一次又超前 1.2 秒, 再补一次, 画面连停三下。
  落点离房主超过 1 秒就再跳一次, 一轮最多 3 次; 补跳过了头 (从落后变成超前或反过来) 就停 (`shouldJumpAgain`)。
  日志 `Together: jumped to the host with a lead of … ms, landed … ms behind`。
- 跟随中这一集从房主的位置打开 (`startPositionMillis`), 不先从头缓冲再跳。
- 加载完先停住: 房主 (房间里有别人在线并且跟随着时) 与跟随的成员 (房主在线时) 这一集第一次加载完不自己开播, 停在开头等大家。
  房主等跟随的成员都在这一集上装好了 (`followersReady`: 片源装进了播放器、不在缓冲; 自由观看的、掉线的不算) 就自己开播,
  最多等 15 秒 (`AUTO_START_TIMEOUT_MILLIS`), 到时没好的照常开播、由跟随的规则追上; 成员跟着房主开播。
  有人还没好时房主那边提示一次 (`TogetherEffect.WaitingForMembers`)。等的途中房主自己按了播放、离开了播放页或房间, 就不再替他开播。
  开播时日志写是哪一种: 成员都好了 (`the following members are ready`), 还是等满了 (`the wait … ran out, not ready: …`, 后面是没好的成员
  —— 成员编号的开头与在做什么, 不写昵称)。
- 房主跳了位置先停住: 房主快进快退、拖进度条确认之后 (播放器的 `PlaybackEvent.SeekCompleted`, 跳完要接着播; 房间里有别人跟随着时),
  停在新位置等跟随的成员在那里缓冲好 (`followersReady` 带 `nearPositionMillis`: 停在房主前后 3 秒以内、不在缓冲) 再接着播, 最多等 10 秒
  (`SEEK_HOLD_TIMEOUT_MILLIS`)。成员已经在落点附近 (换源重装、跳得很近) 不停; 等的途中又跳了就从新位置重新等。
  认「跳了」用播放器的事件而不是拿位置推算: 位置在主线程上取样, 界面卡住时取样会落后好几秒, 推算会以为房主跳了。不这样的话房主当场接着播, 成员重新缓冲完已经落后一截, 又要再跳。等过 1 秒还没好才提示
  (`WaitingForMembers(afterSeek = true)`「正在等待成员缓冲，完成后继续播放」), 跳一下就好的不弹。
- 一次只对一轮: 进页时的那一次对齐与总管发来的指令走的是两个协程, 排着队做, 排到时照最新的房主状态对。
  跳完等播起来量落点的途中房主又变了 (松开长按加速、暂停、又跳了), 就不量了、让出这一轮: 不然新的指令要排在后面等这边缓冲完 (可能好几秒),
  成员这几秒里还照旧的倍速、旧的播放 / 暂停走。
- 播放页不在眼前时不动播放器。

跟随中让路的本机自动行为 (各处读 `Koin.playbackAutomationSuppressed()`): 播完自动下一集 (`SwitchNextEpisodeExtension`)、
回到自己存下的进度 (`RememberPlayProgressExtension`)、自动跳过片头片尾 (`EpisodeViewModel`)、片尾的「接下来播放」卡 (`TvUpNextState`)。

被带到房主那一集的导航 (`TogetherEffect.Navigate`) 由电视根部的 `TvTogetherHost` 执行: 栈里已经有播放页就先退掉它再打开, 不往上叠。
给界面的指示不排队等人, 发的一方从不被卡住: 提示 (`TogetherManager.effects`) 在界面不在时只留最近 16 条;
「去房主那一集」(`TogetherManager.navigations`) 单独留最新的一条, 不会被提示挤掉, 界面的返回栈就位之后才开始取。
攒了一阵才取到的导航先问 `shouldStillNavigate` (房主可能早就换了集)。提示在应用退到后台时不弹, 留下最后一条, 回到前台补上。

### 片源共享

各人自己选源, 而数据源不一定一样; 同一个源在不同的网络下 (防火墙) 也不一定都拿得到播放地址。所以谁的片源先装好, 就把它交给房间
(放进自己的状态 `TogetherWatchingInfo`), 别人这一集的片源还没装好时拿来用。`TogetherSourceHints` (新文件) 管这件事,
`TogetherPlayerExtension` 里只有三处钩子: 取正在播的、等别人交来的、写状态时带上。交两样:

- **播放地址** (`link`: `ExternalLink` = 地址 + 请求头 + 标题): 别人直接播这个地址 (`ExternalLinkMedia`, 见 media-selector.md「别处交来的播放地址」),
  不需要有那个数据源, 也不走「开站点页面、解析出地址」那一步。自己还没选上源、或自动选上的那条还没装好 (还在解析、解析失败) 时就换成它
  (被顶掉的那条不算坏, 不拉黑); 它播不了 (地址绑了 IP、过期了, 或放视频的服务器在这边也连不上) 就换回被顶掉的那条, 没顶掉谁的照常选源。每个地址只试一次。
  一个站点的地址在本机播不了过, 之后 30 分钟里那个站点交来的都不试 (`ExternalLinkMedia.failedHereRecently`, 换了集也一样):
  多半是这边的网络连不上它, 每集再试一遍要白等两三秒, 还会顶掉自己正在装的那条 (工单 54: 成员那边连不上 girigiri, 房主交来的地址两集各试了一次)。
- **播放线索** (`lineage`: `PlaybackLineage`, 见 media-selector.md「播放线索」): 没有能交的地址时的退路 (网盘分享: 取出来的地址绑着账号, 只能各用各的账号),
  自己还没选上源时顺着它在自己的同名数据源里找同一个资源 (`PlaybackLineageSelection.selectAlong`, 与本机线索同一套), 和自己的自动选源同时进行, 谁先选上算谁的。

规则:

- 不用别人的: 自己选的是本机缓存 (最快最稳)、用户自己手动选的、已经装好在播的、已经在用别人交来的地址的 (`replaceable`)。
- 不交的 (`ExternalLinkMedia.shareableOf` / `shareableForTogether`): 只交网页类数据源解析出来的公网地址; BT (用户定: 一起看时速度不稳; 下好的缓存自己照播)、
  网盘取出来的地址与自己网盘里的文件夹、自建媒体服务器 (地址里带访问凭据)、本机代理 (HLS 去广告开着时) 与局域网地址、带 Cookie / Authorization 的都不交。
  收到的地址可以再转交 (第三个人不必等原来那个人); 收之前同样查一遍 (`ExternalLinkMedia.accepts`: 不替房间里的人去取本机、局域网里的东西)。
- 房主的在前, 再看其他人的。别人的线索失效时不忘掉本机记的线索与记住的源; 别人交来的地址不记成这部番的偏好源与播放线索。
- 顺带两边播的是同一个版本, 片头长短、插没插广告都一样, 按秒对齐才对得准。
- 绕不过去的: 放视频的服务器本身在这边连不上 (没有自己的服务器转发)。

### 房间号与密码

`TogetherRoomId` 是房间号 (8 位数字) 加密码 (6 位数字)。房间号是开房间那台设备的设备号; 密码默认随机, 房主可以更换。
`TogetherManager.createRoom()` 打开自己的房间 (界面上叫「开启房间」: 号码与密码不变, 每次开启的都是同一个房间),
`join(房间)` 加入别人的房间 (房间号是自己的设备号时就是打开自己的房间, 密码要对),
`changePassword()` 给自己的房间换一个随机密码 (开着房间时先以「换了密码」关掉再重开)。都在总管自己的作用域里进行: 发起的界面中途没了也照样做完。

邀请是一段话 (控制台的 `RemoteTogether.inviteText`), 房间号与密码都在里面。`TogetherInvite.parse` 从任意一段话里认出它们
(连着的 14 位数字, 或分组写的「4 位 4 位 … 3 位 3 位」), 聊天软件里转来转去、前后多了字也认得出。
邀请的复制与粘贴都在手机上做: 电视弹窗里的二维码是控制台地址加锚点 `#player/together` (`CONSOLE_TOGETHER_ANCHOR`),
扫了直接打开控制台的「一起看」卡片 —— 房主在那里「复制邀请」发给朋友, 朋友在自己电视的控制台里粘贴加入。

### 控制台

`RemoteTogether`: `GET api/together` (状态、房间号、密码、邀请、成员与各人的 `activity`、这台电视是哪个成员 `self`、处境 `situation`、房主播到哪;
正在进房间时 `opening` 说是在开自己的房间还是加入别人的)、`POST api/together/create`、
`POST api/together/join` `number= password=` 或 `invite=<一段话>`、`POST api/together/password` (更换密码)、
`POST api/together/leave`、`POST api/together/follow` `value=1|0`、`POST api/together/transfer` `member=<成员编号>`
(当场回, 状态里 `transferring` 是在等谁接手; `owner` 说这台电视是不是房间的主人, 不是的话卡片上没有「更换密码」)、
`POST api/together/recent/join` `number=` (用电视记下的密码再进最近的房间)、`POST api/together/recent/forget` `number=`。
状态里的 `recent` 是最近的房间 (房间号、房主的名字与编号), 不带密码。
电视是房主时别的在线成员那一行有「转让房主」, 先 `confirm` 一句。

网页上是播放器标签里的「一起看」卡 (`RemoteTogetherPage.kt`): 输入房间号与密码加入, 或把朋友发来的邀请粘贴进输入框直接加入
(局域网页面是 http, 网页读不了剪贴板, 靠用户粘贴时的 paste 事件)。在房间里时照电视弹窗排: 卡头是房间状态的圆点与一句话,
一行标题说此刻在做什么加一句说明 (都照电视算好的 `situation` 写, 页面自己不判断, 与电视弹窗不会各说各的), 下面是房间号、密码与整行的「复制邀请」(直接复制那段话, 走 `execCommand`,
复制不成时露出文本框让人长按复制), 再下面每个成员一张卡片 (首字头像、房主 / 成员、是不是这台电视、在看什么), 底下两颗按钮同电视。
不在房间里时输入框下面列出最近的房间, 每行「加入」与一个 × (从最近的房间里去掉)。地址带 `#player/together` 时打开播放器标签、展开这张卡片。
展开着时每 3 秒读一次状态, 内容没变不重画。失败的提示只有固定的几句 (连不上服务、未能连接到房主、密码不对、正在加入 / 已在房间中、超时),
认不出的错误一律「无法完成操作，请重试。」, 原因写日志, 不把异常的文字与类名露在界面上。

### 回到上次的房间

没离开的房间 (房间号、密码、是不是自己的) 记在设置里, 应用重开后自动回去: 自己的房间当房主重开; 别人的房间当成员加入,
房主不在 (他可能也在重开应用) 就隔一会儿再试, 间隔逐次加倍; 房主说密码不对 (他换过密码) 就忘掉这个房间并提示。
超过 12 小时没回去就忘掉 —— 没有服务器替房间过期。自己从房主让位 (`HostChanged`) 后当成员重新进, 不提示。

### 最近的房间

进过的别人的房间记在本机设置里 (`TogetherSettings.recentRooms`; 增删改是 `TogetherRecentRooms.kt` 里的纯函数): 房间号、密码,
以及在房间里看到的房主的名字与成员编号。最近的在前, 最多 5 个 (`TOGETHER_RECENT_ROOMS_MAX`), 同一个房间号只占一个, 多了最早的那个掉出去。
电视弹窗里选一个, 房间号与密码填进输入框照常加入; 控制台只交房间号, 由电视用记下的密码进 (`TogetherManager.joinRecent`)。

- 只在本机: 不经代理、不发给任何人, 也不知道对方此刻开没开着房间 (没开着时照常是「未能连接到房主」)。
  应用只在房间里时才连代理, 收不到别人主动发来的东西, 所以叫朋友进来仍是发邀请。
- 自己的房间不记 (它有「开启房间」); 被请去临时当房主的那个房间是别人的, 记。
- 房主的名字照房间里名单上的房主记, 名字晚到 (房主的账号信息还没读出来)、改了名都跟着换; 自己当着房主时 (被请去) 不记。
  没有名字的显示成「观众 + 编号头 4 位」, 还没看到过房主的 (下一条旧版本记的) 只显示房间号。
- 房主换过密码: 再进时密码不对, 记下的不动; 电视弹窗清空填进去的密码, 输入新密码进成了就换掉。
- 1.0.9-alpha04 及以前只记上次加入的一个房间 (`TogetherSettings.lastJoined`), 读的时候当作唯一的一个最近的房间, 记下新的时清掉。
- 控制台可以去掉一个; 电视上不删, 靠最多 5 个自己掉出去。和 `TogetherSettings` 别的项一样, 换电视时不搬。

### 测试

- `TogetherManagerTest`: 进出房间、开房间、回到上次的房间、最近的房间 (记哪些、房主的名字、再进、密码换过)、什么时候告诉房间、跟随的各种情形、名单变化、转让房主 (两头各自怎么回房间、作罢、换房主时名单乱的那一阵不提示), 用假的房间。
- `TogetherFollowerPaceTest`: 成员自己的片源跟不跟得上的判定 (什么时候认定跟不上、房主自己跳了照样跟、什么时候再试着跟上)。
- `TogetherPlayerExtensionTest`: 播放页这一侧 (写状态、加载完先停住、从房主的位置打开、跟暂停与倍速、房主卡住时等他), 用假播放器。
- `TogetherSourceHintsTest`: 哪些线索能交、房间里取谁交的、什么时候能换成别人交来的地址; `ExternalLinkMediaTest`: 哪些地址能交、出错后换回去;
  `PlaybackLineageSelectionTest` 里顺着别处给的线索找、失效不忘本机的。
- `RemoteTogetherTest` (ui-tv): 控制台卡片接的接口、文案都有译文、电视二维码的锚点卡片认得、控制台给的邀请认得回同一个房间。
- `TogetherInviteTest`: 房间号与密码的校验, 从各种写法的邀请里认出它们。
- `TogetherRecentRoomsTest`: 最近的房间的顺序、个数上限、再进时留着房主的名字、自己不算房主、旧版本只记了一个的读法。
- `TogetherRoomHostTest`: 名单、版本、消息编解码、位置推算、房间时间。
- `TogetherRoomViewTest`: 成员此刻在做什么、这台设备的处境 (界面上的状态、标题与说明照它们写)。
- `TogetherRoomKeyCacheTest`: 同一个房间号的话题名、同一组房间号加密码的密钥只算一次。
- `TogetherBrokerListTest`: 代理清单只认 `wss://` 地址; 没有清单时开通道前当场拉, 拉不到就以 `TogetherNoBrokersException` 失败。
- `TogetherBrokersFileTest` (desktop): 仓库里的清单每条都认得出, 并留着老版本认的代理。
- `TogetherRoomGatewayTest`: 开房间、加入、房间里没人与密码不对时失败、两个房主怎么收敛、转让房主 (接手、等不到作罢、谁能请谁)、掉线与回来、各人连得上的代理不一样,
  用内存里的 `FakeTogetherHub` (两家代理, 同一个房间号、连着同一家的人互相收得到, 密码不同的解不开, 房主那端回执;
  能断线、只断一家、只连上其中一家、让消息在路上走一会儿、杀应用)。
- `MqttPacketsTest`: 报文的字节形状对着规范写死。
- `MqttLinkTest` / `MqttTogetherChannelTest`: 用内存里的假代理 `FakeMqttBroker` (另写了一份客户端报文的解析, 不借被测的编码器);
  后者也测「解不开」的回执怎么发、怎么对上自己发过的消息。
- `TogetherCryptoTest` / `TogetherPbkdf2Test`: 密钥、加密, 以及慢哈希的两条实现 (系统自带的、自己用 HMAC 算的) 逐字节相同。
- `TogetherLiveBrokerTest`: 连真实的公共代理, 平时不跑, 设 `IZUKO_TOGETHER_LIVE=1` 才跑。
  设 `IZUKO_TOGETHER_PEER_ROOM="<房间号> <密码>"` (一段邀请也行) 时它进那个房间当对端 (每两秒发一条、把收到的打出来), 给设备对测用。
  `TogetherLivePeerTest` 用同样的变量当一起看的成员; 再设 `IZUKO_TOGETHER_PEER_HOST=1` 就开这个房间当房主。
- 在设备上验通道: debug 包控制台的 `api/debug/together/join` `number= password=` 与 `send|state|leave` (`RemoteDebugTogether`, 不经播放器直接进房间收发文本),
  另一头用上面的对端。强停应用 = 异常掉线, 对端应收到遗嘱 (连着几家就收到几份)。
  `POST api/debug/together/dialog` 打开电视上的「一起看」弹窗, 之后用 `api/debug/ui` 读字、送按键走弹窗。
