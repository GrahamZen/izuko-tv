# 播放失败与重试

在线播放出错时分三层处理，从下往上：

1. **数据源**（安卓播放器的 HTTP 数据源）：连接断了、地址过期这类能就地接上的，数据源自己重新请求，播放器看不到错误，画面不断。
2. **播放器的重试**（Media3 的 `Loader` 按 `LoadErrorHandlingPolicy` 重试同一个请求）：数据源接不上时，播放器自己再试几次。
3. **播放失败后的判断**（`decidePlaybackFailure`）：重试也不行、播放器报了错，才判断是这条资源坏了（拉黑、换源），
   还是原地重新加载、等网。

换源本身怎么挑下一条见[选源](media-selector.md)。缓存下载的地址过期另有一套（见[媒体缓存](media-cache.md)「在线源缓存的下载地址」），
什么时候换地址的规矩 `RejectionRefresh` 与播放共用。

## 暂停久了为什么会出错

暂停时播放器攒满缓冲（在线源约 50 秒，见 `ThrottledSourceLoadControl`）就停止读取，读视频的连接空在那里。
服务器常在客户端一分钟不收数据时把连接断掉（nginx 默认的 `send_timeout` 是 60 秒；实测一个在线源的存储服务器停 40 秒没事、60 秒就断）。
断之前已经发出的数据还在本机的缓冲里，接着播之后先读出它们，过二三十秒才撞上断开；
HTTP/2 的服务器断流时把这条流正常收尾，OkHttp 不核对长度，上层只看到「读完了」，提取器在文件中间读不到数据报 `EOFException`。
开着「边下边播」时更糟：Media3 的 `CacheDataSource` 遇到上游没到长度就说读完了，会把那个位置当成文件总长记进缓存，
之后这个地址读到那里就算文件完了，播放器重试、原地重新加载都一读到那儿就报错，最后换源。

签名地址也会过期，但以小时计（在线源约 4 小时，网盘直链约 6 小时），比连接被断少见得多。

## 数据源这一层

单个文件的在线视频（不分块的）由 `createLibassMediaSource` 建数据源，从外到里：

- **断了接着读**（`ResumingHttpDataSource`）：连接空着超过 30 秒（比常见的断开时限短，播放中读的间隔远到不了这么长），
  接着读的那一下不再用它，从已经读到的位置重新请求；读出错（连接被重置、HTTP/1.1 下长度不够），
  或者没到响应说的长度（`Content-Length`，没有时按 `Content-Range` 的总长）就读完了，同样从断处重新请求。
  重新请求前清掉连接池里闲着的连接（`evictIdlePlaybackConnections`）。只接这次打开读到过数据的：一上来就失败的照旧交给播放器，
  坏链接早换源。重新请求本身失败（连不上、服务器出错）也算一次，连接超时用 5 秒（`ReconnectTimeout`，第一次打开仍是 30 秒）。
  第二次起隔 1、2、3、3… 秒再试。至少 3 次、前后至少 10 秒都一个字节没读到时，媒体本身的请求换一次地址
  （`RefreshablePlaybackLink.refreshAfterCutBlocking`，换不换同被拒时的规矩）再试一次；换不了或换了还是读不到就放弃，把错交给播放器。
  放弃时这一轮服务器一次都没回过话（只是连不上、读不到）才记成这条资源接不上了（`RefreshablePlaybackLink.unreachable`，跟第一次播就打不开差不多），
  之后又读到数据时撤销。回了 HTTP 状态说明连得上，不算接不上：说地址不对的（过期被拒、回的不是视频）记成被拒
  （`RefreshablePlaybackLink.rejected`，要打开网页现抓的源只能重新解析换地址，见下文「地址过期时在后台重新取」），服务器出错的交给下文的判断。撑 10 秒是为了扛住网络抖一下（切换热点、路由器重拨）；也不能更久：要赶在暂停时攒下的缓冲（约 50 秒）
  放完之前判完，加载方才来得及在后台换源（见下文「确认接不上时换源」）。连不上时约 12 秒放弃，服务器不应答时每次等满连接超时，约 18 秒。
  加载被取消时线程被打断，不算断流。
  调试开关 `resumeCutStreams`（默认开）关掉时这一层直接透传。
- **地址被拒换地址**（`RefreshingHttpDataSource`）：重新请求（包括上一条的）被拒绝时换地址重试，缓冲里还有内容时画面不断。
  `PlayerSession` 加载资源时给它登记怎么换（`PlaybackLinkTracker` → `PlaybackLinks`，重新解析走 `MediaResolver.resolveFreshLink`，
  要开网页现抓的源不在这里解析）；换不换、何时不再换同缓存下载，按共用的 `RejectionRefresh`。只有请求成过的地址才换，
  一上来就被拒的照旧报打开失败；换不了、换了也没用时被拒的错原样交给播放器。重新解析最多等 15 秒：被拒的那个请求这时停着，
  而被拒不一定是过期。换来的地址得是同一个文件：响应里的文件总长与先前不一样（另一条线路或清晰度）时，接着按原位置读会读出对不上的数据，
  这时把请求按被拒（412）报给播放器，走下表的原地重载。
- **OkHttp**（`createPlaybackHttpDataSourceFactory`）：按代理与连接超时共用客户端与连接池，读超时 8 秒。

开着「边下边播」时这几层外面还有一层 `CacheDataSource`（见 `PlaybackDiskCache`）。上面两条保证断流到不了它那里：
接着读接上了它看不出断过，接不上时交出去的是错误而不是「读完了」，它不会把断的位置当成文件总长。
以前断流时记下的错总长，每次打开在线视频时先忘掉（`PlaybackDiskCache.forgetContentLength`），总长由这次的响应重新给。

网盘直链（解析器要求分块并发的）走 `ParallelRangeDataSource`：每块是一个范围请求，块读到一半断了（`Connection ended early`）
由 `ParallelRangeReader` 自己重试，地址被拒同样经 `RefreshingHttpDataSource` 换地址，不套「断了接着读」。
m3u8 的分片各有地址，不在数据源里换地址，过期时走下表的原地重载。经本机 HLS 代理播放时源站回的 HTTP 错误由代理原样转给播放器
（`upstreamErrorResponseHeader`），过期才认得出。

分享、同步播放要的「现在的地址」按 `PlaybackLinks.currentUriOf` 取，同步播放的媒体标识也按它算，播放器换了地址手机跟着重新要。

## 播放器的重试

`OpeningLoadErrorPolicy`：打开媒体期间（`setMediaData` 到读出音视频轨）读取出错只重试一次，重试也不会好的错
（401 / 403 / 404 / 410、域名解析不出）不重试，坏链接约一秒就换源；打开之后按 Media3 默认，重试 3 次、逐次多等。
重试间隔一律用 Media3 默认的，不能改成 0：加载器只在等下一次重试的间隙里留着错误，间隔为 0 时错误永远报不出来，坏链接被一直重试下去。

加载出了错播放器先自己重试，重试也不行才报播放失败；每次加载出错 `LoadErrorLog` 记一行（主机、读了多少、什么错），
播放失败时看得出是一次就坏了，还是重试了几次都没接上。

### iOS：等数据卡死时经本机代理原地重开

AVPlayer 自己连源站的连接会坏一阵：想播、在等数据，已缓冲的部分一点也不长、也不报错；原地 seek、往后跳之后新要的那段一个字节也拿不到，
同一地址新建播放项一秒内就报网络错（被当成坏源拉黑、换源），两三分钟后同一地址又能正常打开。同一时刻这台设备用应用自己的
HTTP 客户端取那一段是通的（iPad 播网页源的 mp4 实测，源站是 HTTP/2 的 CDN；同一集每次播到同一处附近就卡）。

平常播放由 AVPlayer 直连源站。`IosDataStall`（由 `IosVideoLayerWake` 盯着）在缓冲 8 秒一点没长时请求原地重开（`PlaybackStallReopen`）；
`PlaybackStallReopenExtension` 收到后在 `StalledMediaRoute` 记下这个播放器卡在这条资源上，再 `reloadCurrentMedia` 重新取地址、回到卡住的位置，
不拉黑、不换源。`PlayerSession` 装资源时问 `ParallelRangePlayback`：是记下的那条、公网地址（地址不带 `.m3u8`、内容不是播放列表、源站认范围请求）
就经本机代理播（网盘原文件多连接取用的同一套）：AVPlayer 只连 `127.0.0.1`，代理用应用自己的客户端开两条通道，按块向源站要准范围，
读到一半断了、读超时（15 秒没数据）或源站回得比要的短，从断开处接着要；一点没拿到就出错的重试 3 次。
这个播放器之后再装同一条（地址过期、断网恢复后重装）也经代理；装了别的资源（换集、换源）就忘掉那条，回到直连，播放会话关掉时也忘掉。
本机与局域网的地址、HLS 不经代理，重开就是直连重开。片源慢不算卡死：慢的时候缓冲在长。

重开在同一处（前后不到 60 秒）最多连着 3 次、两次至少隔 20 秒；往下播过 60 秒再卡算另一处。每次请求重开都记一行 `[AVStall]`，
带 AVPlayer 自己的传输记录（下了多少、实测码率、连的哪台服务器）；缓冲用完卡住时（AVPlayer 的「卡住」通知）记 `[AVError] 缓冲用完卡住`；
经代理时记 `[RangeProxy] 等数据卡死过, 这次经本机代理交给播放器`。

## 播放失败后怎么办

播放器报错或加载失败时，换不换源只由 `decidePlaybackFailure`（`PlaybackFailureRecovery.kt`）决定，按下表从上到下取第一条；
数据源画像（`SourceProfileExtension`）用同一个判断，只有「换源」才记这条资源的失败。

| 情况 | 处理 |
| --- | --- |
| 正在后台换源时播放器报的错（旧的那条缓冲放完了，见下文「确认接不上时换源」） | 不处理：新的已经在装 |
| 正在等网（选源会话重建时接着等） | 接着等 |
| 加载被取消（换集、离开播放页、改选） | 不算失败：选中的可能已经是新选的那条，接着加载的另有其人 |
| 网页引擎不可用 | 换源没用，保留报错 |
| 离开播放页时释放 Surface 超时 | 与资源无关，不处理 |
| 拖动预览换输出弄坏了解码器（`SeekPreviewDecoderFault`） | 等 3 秒原地重载，不拉黑 |
| 解码器被抢走（`isDecoderPreempted`），这条资源还没因此重载过 | 原地重载，不拉黑 |
| 断网（见下） | 不拉黑、不换源、不限时长，恢复后原地重载；隔 30 秒不管系统怎么说都试一次 |
| 数据源已经确认这条资源接不上了，也已经为它在后台换过源（没换成，见下文「确认接不上时换源」） | 拉黑并换源，不再原地重载 |
| 这条资源播起来过、30 分钟内没重取过，且地址被拒绝（HTTP 401 / 403 / 404 / 410 / 412）、回的不是视频，或连接中途断了（`isStreamInterrupted`） | 原地重载，不拉黑 |
| 其余 | 拉黑并换源 |

设置「播放失败时自动换源」关着时上表照常判断，原地重载、重新取地址、等网照做，只有「拉黑并换源」不做，停在报错上
（`SwitchMediaOnPlayerErrorExtension.recoverInPlaceOnly`）：这个开关只管换不换源。

原地重载走 `reloadCurrentMedia` → `PlayerSession.loadMedia`，地址重新解析，回到出错前的进度与播放意图；这条资源还没打开过时回到记忆的进度并开播。
「连接中途断了」指连上过的连接读不下去了：读到一半没数据了（`EOFException`）、读超时、连接被重置、HTTP/2 的流被重置；
根本连不上（主机连不上、域名解析不出）不算，那是站点的事。到这一步时数据源已经接过、播放器也重试过，原地重载换一个新地址、新连接再来一次。
30 分钟的间隔防止放到坏掉的那一段（分片没了、文件残缺）时出错、重取、放到同一处又出错，没完没了：刚取的地址又被拒就不是过期，
刚重取过又断也不是暂时的，这时换源。

断网只认系统明确说没网（`NetworkStatus`，默认网络没了或被省电模式拦着）。系统的联网检查在国内网络下不一定准，不用它，所以路由器连着但外网不通时分辨不出，照常换源。
系统的状态也可能误报：服务器回了 HTTP 状态就算网是通的，不算断网；等网时隔 30 秒试一次，误报时也不会一直等下去。
连接报「网络不可达」（`ENETUNREACH`）时系统可能还没跟上，等 1.5 秒再看系统；这时还说有网就不算断网（连 IPv6 地址而这个网络没有 IPv6 路由时也报这个）。
断网恢复后 20 秒内的网络类失败（解析超时、连不上）也算断网造成的，解析在断网时开始、恢复后才超时；每次断网只算一回，恢复后这条资源再失败就照常换源。
等网期间加载状态是 `VideoLoadingState.WaitingForNetwork`，播放画面上提示恢复后自动继续，可以手动换源或退出。

还没选中资源时断网（切集、开播时）由 `SearchAfterNetworkOutageExtension` 管：在线源全部搜索失败时画面不说「都没有找到这一集」，同样提示在等网；
数据源照常查，本地缓存不要网，选中了照常放；手上有旧结果的源也可能被自动选中，而记住的源因为搜索失败排不上。
恢复后播放还没起来、也不是用户自己选的，就重建查询会话（`MediaFetchSessionRefresh`）重新搜索，自动选源跟着从记住的源重来；用户选的资源等网后接着放。
断网时的搜索失败不记进数据源画像。
其余只读内容（分集信息、弹幕、评论等分页列表、详情页、时间表）恢复后由 `FailedReadRetry` 通知各自重试失败了的部分，已经取到的不动；写操作不接。

## 确认接不上时换源

数据源把正在播的这条记成接不上时（`PlaybackHandover.unreachable`），播放器里通常还有几十秒缓冲。`PlaybackFailureRecovery` 不等缓冲放完报错，
等往前的缓冲只剩约 20 秒（`SWITCH_AHEAD`，播放器不报缓冲位置时不等）就照常换源（`SwitchMediaOnPlayerErrorExtension.switchUnreachable`：
拉黑这条、按播放失败换源的规矩选下一条，包括放开被暂停的搜索）。不一判出来就换：外网断了一会儿而系统没报（路由器连着、上游在重拨）时
数据源也会判成接不上，这期间播放器自己一直在重试，网回来就接着读、数据源撤销「接不上」，这边跟着作罢；剩的 20 秒留给找下一条、解析它。
网断着或刚断过（20 秒内）时不换，是断网的事；断网刚开始时系统要过一会儿才报，先等 1.5 秒再看（同上文断网的判断）。
用户拖入的文件、别处交来的地址、不优先在线源（报错时也不自动换）的不这样换（`PlayerLoadErrorHandler.switchesAutomatically`），
照旧等它报错、按上表处理（原地重载）；上表「已经确认接不上」那一行也只对这样换过的生效。

选中项变了之后 `PlayerSession.loadMedia` 照常装新的那条，但播放器里那条正常播着、又已确认接不上时，不先停下它（`PlaybackHandover.begin`）：

- 新的解析、打开期间旧的接着放，加载状态仍是旧的「已装好」，画面照常；`PlaybackHandover.preparing` 是正在准备的那条。
  这期间播放器里的状态都算旧的：失败处理不把旧的在播记成新的播起来过（新的打不开时照常换源，不先原地重载），记住的源、数据源画像、
  一起看交给房间的片源都等换下来再按新的算。
- 新的拿到了先试一下能不能打开（`HandoverLinkCheck`：只要第一个字节，被拒、回的是网页、10 秒内连不上都算打不开），打不开就不换，
  同下文「装不成」；能打开再停下旧的，从旧的最后播到的位置（`RememberPlayProgressExtension.startPositionMillis` 在这一刻再问一次）、照它的播放意图
  （这期间暂停了就停着）装进播放器。播放器只有一个，装新的时重新缓冲一两秒的停顿免不了；剩下的旧缓冲直接丢掉。
- 新的在换下来之前就装不成（解析、打开失败）时旧的接着放，不报失败（`PlaybackHandover.failures`）：换源那边拉黑新的、选下一条，
  同样在后台装。断网时新的当然装不上，不是它的错：不拉黑、不接着换，旧的放完后按断网处理。换下来之后新的才在播放器里出错的，照常换下一条，那时旧的已经停了。
- 旧的缓冲先放完报错时，停下它，加载状态改成正在解析，新的拿到后照样从那个位置接着放。这个错不算播放失败（上表第一行），数据源画像也不记。
- 换的途中又改选了别的（选中项变了、上一次装被取消），旧的照样接着放，新选的那条同样在后台装。

开始在后台换时发一次 `PlaybackHandover.started`（换的途中又改选别的不再发），电视上由 `TvPlaybackHandoverToasts` 弹提示：
当前资源无法继续加载，正在后台换，已缓冲的内容会继续播放。没选出别的资源时不提示，缓冲放完后按上表换源（同样选不出就停在报错）。

## 地址过期时在后台重新取

要打开网页现抓的源（以及别的数据源层换不了地址的）暂停很久后接着播，地址多半已经过期，重新请求被拒。数据源把它记成被拒
（`PlaybackHandover.rejected`）时，`PlaybackFailureRecovery` 不等缓冲放完报错再原地重载，当场原地重载（`reloadCurrentMedia`，地址重新解析）；
`PlayerSession.loadMedia` 装的是同一条、它的地址又被拒了，同样不先停下它（`PlaybackHandover.begin`）：旧的接着放，拿到新地址、试过能打开再换下来，
从当时的位置接着放，不弹提示。规矩同上表的原地重载：30 分钟内重新取过又被拒说明不是过期，能自动换的趁缓冲还在播换源（同上节），不能的照旧等它报错。
重新解析不出来、新地址打不开的，能自动换就换下一条（同上节「装不成」），旧的接着放。
